# Cache-aware inference foundation

This bundled, opt-in plugin establishes the contract Hermes needs before an
inference backend can save, restore, or route by KV-cache checkpoints.

It does **not** pretend that KV tensors have a universal file format. Instead it
provides deterministic identifiers and durable operational state that a pinned
llama.cpp controller, LM Studio-managed cache, Ollama instance, or fleet proxy
can consume.

## Enable

```bash
hermes plugins enable cache-foundation
hermes cache status
```

The plugin affects only `chat_completions` requests sent to trusted local
endpoints by default. Remote endpoints receive no Hermes cache headers unless
the operator explicitly sets `HERMES_CACHE_ALLOW_REMOTE=1`.

## What it does

For each eligible provider request, Hermes computes:

- a checkpoint ID tied to the model/runtime/template/KV format;
- the exact system-prompt and static-prefix hashes;
- a tool-schema hash;
- a request-prefix ID for all replayed messages before the newest item;
- an endpoint-normalized session affinity record.

It adds only hash/identifier headers:

```text
X-Hermes-Cache-Schema
X-Hermes-Cache-Checkpoint-Id
X-Hermes-Cache-Prefix-Id
X-Hermes-Cache-System-Hash
X-Hermes-Cache-Static-Hash
X-Hermes-Cache-Tool-Hash
X-Hermes-Cache-Engine
X-Hermes-Cache-Mode
X-Hermes-Cache-Session-Id
```

No prompt text, tool payload, response text, or API key is written to the state
database. Session IDs are disclosed only to endpoints considered local/private.

## Commands

```bash
hermes cache status
hermes cache status --json
hermes cache inspect --session SESSION_ID
hermes cache checkpoints
hermes cache doctor --endpoint http://x1-370:8080 --provider custom
hermes cache clear --session SESSION_ID
hermes cache clear --checkpoints
```

Warm a deterministic system prefix explicitly:

```bash
hermes cache warm \
  --endpoint http://x1-370:8080 \
  --model qwen3.5-35b-a3b \
  --prompt-file ~/.hermes/cache/prompts/primary-cli-coding.txt
```

Warmup sends a one-token OpenAI-compatible request. It does not claim that the
backend persisted a disk checkpoint; it marks the inventory as `warmed`. An
engine adapter should later update the inventory to `written`, `restored`, or
`hit` based on real backend evidence.

## Runtime fingerprinting

The default manifest uses the provider/model identifiers available to Hermes.
For reproducible on-disk checkpoints, set the exact deployment identity:

```bash
export HERMES_CACHE_ENGINE_ID=llama.cpp
export HERMES_CACHE_ENGINE_FINGERPRINT=llama.cpp-b6123
export HERMES_CACHE_MODEL_FINGERPRINT='Qwen3.5-35B-A3B-Q4_K_M:sha256:...'
export HERMES_CACHE_CHAT_TEMPLATE_HASH='sha256:...'
export HERMES_CACHE_KV_FORMAT='q8_0-k/q4_0-v'
```

A change to any of these values produces a new checkpoint ID. This prevents a
checkpoint generated by different weights, tokenizer/template, engine build, or
KV representation from being treated as compatible.

## State

The default database is:

```text
$HERMES_HOME/cache/state.db
```

Override it with `HERMES_CACHE_STATE_DB`. SQLite stores:

- current session-to-endpoint affinity;
- checkpoint inventory and observed state;
- request duration and token counters;
- provider-reported cache-read/cache-write token counts.

## Routing contract

`agent.cache_foundation.CacheRouteCandidate` implements a deterministic scoring
model where the priority is:

1. the node already holding the session;
2. a compatible checkpoint on the node;
3. the model already loaded;
4. queue/prefill/cold-load cost;
5. network latency.

This PR does not silently replace Hermes' provider client or move a live session
between machines. A future fleet provider/proxy consumes the manifest headers
and the same scoring contract, then reports actual checkpoint state back to the
inventory.

## Relationship to RTK, Headroom, and Neo4j

- **RTK** reduces terminal output before it enters the conversation.
- **Headroom** will compress the volatile/live message zone in a later plugin.
- **Neo4j** remains durable semantic and relational memory.
- **This plugin** identifies and measures inference-prefix/KV reuse.

Keeping these boundaries separate avoids double compression and prevents a
context optimizer from rewriting the prefix whose KV state the backend is
trying to reuse.

## Environment variables

| Variable | Purpose |
| --- | --- |
| `HERMES_CACHE_DISABLE=1` | Disable middleware while keeping CLI access |
| `HERMES_CACHE_ALLOW_REMOTE=1` | Send identifiers to a trusted remote proxy |
| `HERMES_CACHE_MODE=prefer` | Cache policy hint sent to the endpoint |
| `HERMES_CACHE_STATE_DB=/path/state.db` | Override SQLite path |
| `HERMES_CACHE_ENGINE_ID` | Exact engine family/control-plane ID |
| `HERMES_CACHE_ENGINE_FINGERPRINT` | Engine build/version fingerprint |
| `HERMES_CACHE_MODEL_FINGERPRINT` | Weights/quant/tokenizer identity |
| `HERMES_CACHE_CHAT_TEMPLATE_HASH` | Exact serialized chat-template hash |
| `HERMES_CACHE_KV_FORMAT` | KV types/layout identity |
| `HERMES_CACHE_API_KEY` | Optional key used only by explicit `cache warm` |
